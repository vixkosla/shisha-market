# MCP для пользователей и оператора

Обычные пользователи подключают `mcp/user.mjs`: инструкция [на сайте](https://shisha-market.com/mcp), вход по своей почте и подтверждение доступа в [кабинете](https://shisha-market.com/account/mcp). Ключ оператора им не нужен. Клиент сохраняет отдельный отзывной личный ключ; API разрешает работу только с собственными объявлениями и сохраняет обычные согласия и модерацию. Это локальный stdio-клиент, не удалённый HTTP endpoint.


## Служебный MCP для оператора

Документация для оператора опубликована на сайте: `https://shisha-market.com/mcp/operator`. Оттуда же скачивается клиент: `/mcp/listings.mjs` (копия проверяется тестом на совпадение с `mcp/listings.mjs`).

Локальный MCP `mcp/listings.mjs` вызывает `https://shisha-market.com/api/operator/listings` с токеном оператора. Токен не входит в git.

Файл токена: `~/.config/shisha-market/operator.token`. На сервере то же значение в `OPERATOR_TOKEN`.

Инструменты: `create_listing`, `list_pending`, `get_listing`, `get_listing_photo`, `update_listing`, `archive_listing`, `moderate_listing`. Это закрытый путь оператора, не пользовательская авторизация: ключ не раздаётся продавцам. Сначала оператор один раз входит на сайт своей настроенной почтой и принимает актуальные документы; иначе API честно сообщает, что аккаунт оператора ещё не готов.

Клиент использует стандартный newline-delimited stdio и согласует MCP 2025-11-25 либо совместимую старую версию. Ответы с `Content-Length` оставлены только для явно таких же входящих запросов. Подключение проверяется настоящим `Client`/`StdioClientTransport` официального SDK, а не только собственным парсером.

Полный путь: `create_listing` с `publish: false` → `get_listing` → `get_listing_photo` для каждого фото → человеческое решение через `moderate_listing` с актуальным `revision`. При отказе `update_listing` исправляет собственную карточку и снова отправляет её на проверку. После одобрения карточка и фото становятся публичными; `archive_listing` снимает собственную публикацию с сайта. Возвращаются `id`, `status`, `revision` и ссылка на карточку; `get_listing` отдельно показывает реальную публичную видимость и комментарий модератора.

Фотографии: 1–6 локальных JPG/PNG/WebP, суммарно до 8 МБ новых файлов. Клиент проверяет размер и сигнатуру до отправки; сервер независимо проверяет содержимое и общий размер, снимает метаданные и ограничивает JSON-запрос 12 МиБ, в том числе без `Content-Length`. В `update_listing` пропущенные поля и фото сохраняются; `keepPhotoIds` позволяет исключить старые, а новые файлы добавляются в конец. Чужие и архивные карточки редактировать нельзя.

Публикация по умолчанию остаётся на проверке. `publish: true` — отдельное явное решение, делающее карточку публичной. Если на сервере включена автопубликация ВК, одобрение может отправить пост туда; `archive_listing` сам по себе не удаляет существующий пост ВК. Не повторяйте создание вслепую после сетевого таймаута — сначала проверьте очередь, чтобы не получить дубликат.

После миграции `0003_listing_revisions.sql` очередь возвращает `revision`. Передавайте этот номер в `moderate_listing`, `update_listing` и `archive_listing`. Без номера или при устаревшей версии действие отклоняется: заново получите карточку и проверьте изменённый текст и фото. Не подставляйте автоматически свежий номер в старое решение. Изменений схемы для расширенного пути не требуется; проверка клиента и серверный выпуск фиксируются отдельно.
